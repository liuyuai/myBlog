# HITL 人在回路：给 Agent 装上"确认闸门"


> 「AI Agent 工程实践」系列第 6 篇，Agent 的安全网。
> 上一篇：[意图路由](./intent-routing.md)
> 系列起点：[手写一个 Agent](./agent.md)

## 什么是 HITL

HITL（Human-in-the-loop，人在回路）指：**在 Agent 执行的关键环节插入人工确认/干预**，由人决定"继续、修改还是中止"。

为什么需要它？因为 Agent 有个致命特性：**链式执行会放大错误**。第一步的小幻觉会被后续步骤不断引用、加工，最后输出一个看起来很对、其实全错的结论。对资金操作、删除、对外发布这类**不可逆动作**，让 Agent 全自动执行等于裸奔。

```
全自动:   Agent ──→ 付款 1000 元           ← 参数填错没人拦
HITL:     Agent ──→ [确认] 付款 1000 元?    ← 人点头才执行
                         └─ 是/否/改金额
```

## 什么时候需要 HITL

| 操作类型 | 示例 | 是否需要确认 |
| --- | --- | --- |
| 资金操作 | 付款、转账、改价 | **必须**（执行前） |
| 破坏性操作 | 删除文件/数据库、清空数据 | **必须**（执行前） |
| 对外发布 | 发邮件、发帖、推送通知 | **必须**（或发布后复核） |
| 敏感数据访问 | 读取客户隐私、内部机密 | **必须**（授权确认） |
| 常规操作 | 查询、计算、生成草稿 | 不需要 |
| 批量低风险 | 格式化整理、批量打标签 | 抽查复核即可 |

规律：**不可逆、有资金/合规/声誉影响的操作，一定要有人把关**。

## 四种介入模式

| 模式 | 介入时机 | 风险控制 | 效率 | 典型场景 |
| --- | --- | --- | --- | --- |
| 执行前审批 | 动作执行前 | 最高 | 低 | 付款、删除、发布 |
| 关键节点检查点 | 长任务中间暂停 | 中高 | 中 | 多步报告、跨系统操作 |
| 执行后复核 | 动作完成后抽查 | 中 | 高 | 批量低风险任务 |
| 升级转人工 | 低置信/异常时移交 | 高 | 中 | 投诉、无法处理、意图不明 |

注意：**复核不是确认**——执行后复核只能止损，拦不住已经发生的影响。不可逆动作必须用"执行前审批"。

## 实现：一个最小确认机制

### 第一版：同步确认（终端场景）

```js
async function runStep(step) {
  if (step.risk === 'high') {
    const ok = await askHuman(`确认执行：${step.desc}？[y/n] `);
    if (!ok) return { status: 'CANCELLED' };
  }
  return execute(step);
}
```

能用，但真实场景几乎都是异步的：**Agent 跑在服务端，人坐在客户端**，等一个 `y/n` 不现实。

### 第二版：中断 + 恢复（生产模式）

生产模式的标准做法是"**中断点（interrupt）+ 恢复（resume）**"：Agent 遇到需要确认的动作，保存当前状态并挂起，返回一个待确认任务；人工确认后，从断点继续执行。

```js
let pending = null;                    // 待确认任务

async function agentLoop(task) {
  for (const step of task.steps) {
    if (step.requiresApproval) {
      // 保存现场，挂起等待人工
      pending = {
        id: step.id,
        desc: step.desc,
        risk: step.risk,
        resume: () => execute(step)    // 确认后从这一步继续
      };
      return { status: 'WAIT_APPROVAL', id: step.id, desc: step.desc };
    }
    await execute(step);
  }
  return { status: 'DONE' };
}

// 人工确认接口（前端按钮/审批流调用）
async function approve(id, decision) {
  if (pending?.id !== id) return { status: 'NOT_FOUND' };
  if (decision === 'approve') return pending.resume();   // 批准 → 从断点继续
  if (decision === 'reject') return { status: 'REJECTED' };  // 拒绝 → 终止
  if (decision === 'edit') return { status: 'EDIT_REQUIRED' }; // 要求修改 → 回退
}
```

三个关键点：

1. **保存现场**：挂起前把已完成的步骤和待执行的步骤都存好，确认后**从断点继续，而不是从头重跑**；
2. **确认结果作为输入**：人工的修改意见要能回传给 Agent 继续执行；
3. **超时策略**：人工迟迟不确认，要有一个默认行为（见下）。

（LangGraph 的 `interrupt()` / `Command(resume=...)` 就是这个模式的内置实现，原理相同。）

## 设计要点

1. **给足决策上下文**：确认弹窗至少要包含"要做什么、影响什么、风险提示"，最好附 Agent 的推理摘要。信息不足，人工只能瞎点；
2. **超时默认策略**：安全优先（超时自动拒绝）还是效率优先（超时自动通过），按风险等级定——付款类超时一律拒绝；
3. **会话恢复**：确认后从断点继续，已完成步骤不重跑（省 token 也省时间）；
4. **审计日志**：记录谁、什么时候、确认了什么、Agent 后续做了什么——这是合规和追责的底账；
5. **减少打断**：低风险步骤合并成批量确认、给"本次会话内同类操作不再询问"的选项，别让确认框淹没用户。

## 分级策略

把 HITL 做成可配置的，而不是写死的：

| 风险等级 | 策略 |
| --- | --- |
| 低 | 全自动执行 |
| 中 | 关键节点检查点（长任务中间确认一次） |
| 高 | 执行前审批 + 全程可中止 |

配合 [意图路由](./intent-routing.md) 的兜底：低置信、情绪激烈、Agent 反复失败的请求，直接升级转人工。

## 注意

1. **HITL 是安全网，不是拐杖**：每个步骤都要人点头，Agent 就退化成"打字员"，自动化的价值全没了。确认点宁少勿多，只在真正不可逆的地方设闸；
2. **确认信息不足 = 形式主义**：人工没有足够上下文时，确认只是走过场，出了事照样追责到人；
3. **确认结果要进日志和状态**：别让确认只是"点了一下"，后续审计和复盘都需要它。

## 总结

HITL 的本质是**用人的判断兜住模型的不确定性**，核心三件事：**不可逆动作执行前审批、长任务关键节点中断恢复、低置信转人工**。加上可配置的分级策略和审计日志，一个能上生产的 Agent 安全网就齐了。
