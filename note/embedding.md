# Embedding 与向量检索

> 「AI Agent 工程实践」系列 · 基础篇第 2 篇。
> [RAG](./rag.md) 篇和[意图路由](./intent-routing.md)篇把"向量化"当黑盒用，这篇拆开讲。
> 相关：检索基础 / 多轮记忆压缩

## 什么是 Embedding

Embedding（嵌入）是把一段文本映射成**固定维度的数值向量**（如 768 / 1024 / 1536 维），核心性质是：

> **语义相近的文本，向量在空间中距离近；语义无关的，距离远。**

"苹果"和"iPhone"的向量距离，应该小于"苹果"和"宇宙飞船"——但要注意，"苹果"同时指水果和公司，这类歧义本身就让 embedding 很难完美。

一句话：embedding 把"语义"变成了"坐标"。

## 余弦相似度

衡量两个向量方向是否接近，值域 [-1, 1]：

```js
function cosine(a, b) {
  let dot = 0, na = 0, nb = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i]; na += a[i] * a[i]; nb += b[i] * b[i];
  }
  return dot / (Math.sqrt(na) * Math.sqrt(nb) + 1e-9);
}
```

工程上，很多向量库存的是 **L2 归一化向量**，此时"点积 = 余弦相似度"，检索可以算得更快。

## 为什么语义相近 → 向量相近

Embedding 模型（sentence-transformers、各云厂商 embedding API 等）通过海量"相似文本对"训练，学到的是：

> **在相似上下文里出现的文本，映射到向量空间里的相邻位置。**

但要记住它的本质局限：embedding 学的是**分布相似**，不是**事实正确**。专有名词、ID、代码、精确数字这些"字面精确"的东西，向量检索经常失效——这正是[检索基础（BM25）](./retrieval-basics.md)存在的理由。

## 检索流程

```
离线建索引：文档 → 切分 → 每块 embedding → 存入向量库
在线检索：  query → embedding → 向量库找 Top-K 近邻 → 送入 LLM
```

数据量不同，检索方式不同：

| 数据量 | 方案 | 说明 |
| --- | --- | --- |
| 千级 | 内存数组 + 暴力计算 | 直接遍历算相似度，原型够用 |
| 万级 | pgvector（PostgreSQL 插件） | 已有 PG 时最省事 |
| 百万级 | faiss（库） | 需要自己管服务 |
| 生产级 | 专用向量库（Milvus / Qdrant / ES 等） | 多租户、过滤、高可用 |

大规模场景用的是 **ANN（近似最近邻）**，如 HNSW、IVF：牺牲少量精度换速度，别指望它返回"绝对最优"。

## 向量数据库怎么选

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 原型 / 小数据 | 内存数组 | 零依赖 |
| 已有关系库 | pgvector | 少一个组件 |
| 海量 + 过滤 | 专用向量库 | 元数据过滤、水平扩展 |

## 注意（坑）

1. **维度高不等于好**：embedding 模型与领域匹配更重要，通用模型对医疗/法律/代码表现差；
2. **检索要用检索专用模型**：别拿对话模型的 embedding 接口混用（维度、质量都不同）；
3. **确认归一化约定**：余弦还是点积，库的文档说了算；
4. **增量更新**：新文档要增量或重建索引，否则永远搜不到新知识；
5. **绝对阈值不靠谱**：向量距离只适合做"相对排序"，硬阈值要按你的数据实测。

## 总结

Embedding 把语义变成坐标，余弦算距离，向量库做检索。它是 RAG 和语义路由的引擎，但解决不了精确匹配——下一篇讲"字面匹配"的黄金标准：[检索基础：BM25](./retrieval-basics.md)。
