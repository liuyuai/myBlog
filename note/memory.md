# 记忆系统：让 Agent 记住用户与任务

> 「AI Agent 工程实践」系列 · 进阶篇第 1 篇。
> [RAG](./rag.md) 解决"外部知识"，记忆解决"用户与任务的历史"。
> 相关：[手写 Agent](./agent.md) / [多轮记忆压缩](./memory-compression.md)

## 为什么需要记忆

没有记忆的 Agent 每次对话都是"失忆患者"：不知道用户叫什么、偏好什么、上次做到哪一步。记忆分两类：

- **短期（工作记忆）**：当前任务的上下文 = messages；
- **长期（持久记忆）**：跨会话的用户画像、历史结论、偏好。

## 记忆的分类

| 类型 | 内容 | 实现 |
| --- | --- | --- |
| 工作记忆 | 本轮对话 / 任务上下文 | messages（原生上下文） |
| 情景记忆 | 过去发生过什么（上次问过什么） | 摘要 / 向量库 |
| 语义记忆 | 用户偏好与事实（是前端、喜欢简洁） | 结构化 KV / 数据库 |

## 记忆的实现层次（由简到繁）

1. **原生上下文**：全部历史塞进 messages——简单，但窗口有限、成本高；
2. **摘要记忆**：把旧对话压成摘要，需要时注入——省 token、丢细节（见[多轮记忆压缩](./memory-compression.md)）；
3. **向量记忆**：历史对话/事实向量化，按相关性检索注入——可扩展、能"想起来"；
4. **结构化记忆**：用户画像表、任务状态表（KV / 数据库），按字段精确读写。

## 一个最小实现（JS 示意）

```js
// 对话结束时：抽取事实写入记忆库
async function remember(messages, memoryStore) {
  const facts = await callLLM({
    messages: [{
      role: 'user',
      content: `从对话中抽取用户事实（姓名/职业/偏好/待办），只输出 JSON：
{"facts": [{"key": "...", "value": "..."}]}
对话：${JSON.stringify(messages)}`
    }]
  });
  const { facts: list } = JSON.parse(facts);
  for (const f of list) memoryStore.set(f.key, f.value);   // 结构化记忆
}

// 新对话开始时：检索相关记忆注入 system
async function buildSystem(userId, memoryStore) {
  const facts = memoryStore.all(userId);                   // 或向量检索 Top-K
  return `你是助手。以下是你对这个用户的了解：\n${facts.map(f => `- ${f.key}: ${f.value}`).join('\n')}`;
}
```

## 写入 / 检索 / 更新 / 遗忘

| 环节 | 关键问题 |
| --- | --- |
| 写入 | 什么时候记？任务结束、关键信息出现时 |
| 检索 | 注入什么？只注入相关的，别把全部记忆塞进上下文 |
| 更新 | 冲突怎么办？用户改口时新值覆盖旧值 |
| 遗忘 | 隐私与过期：能查、能删，用户要求遗忘时立即清除 |

## 与 RAG 的区别

| | RAG | 记忆 |
| --- | --- | --- |
| 数据来源 | 外部知识库 / 文档 | 用户历史 / 任务状态 |
| 更新频率 | 低频（文档变更才更新） | 高频（每轮都可能变） |
| 个性化 | 无 | 强 |

## 注意（坑）

1. **记忆注入挤占上下文**：注入前要裁剪（配合压缩篇）；
2. **记错比不记更糟**：事实抽取错误会污染后续所有对话，关键事实写入前可自检或人工确认；
3. **隐私**：长期记忆必须支持查看与删除；
4. **向量库复用注意**：记忆索引和 RAG 索引可以共用一个库，但一定要区分 namespace 或标签，别串数据。

## 总结

记忆 = 短期上下文 + 长期画像。实现顺序：先摘要、再向量、最后结构化。下一篇解决记忆的"瘦身"问题——[多轮记忆压缩](./memory-compression.md)。
